# HASS-FAST-1: the 👀 on receipt, per-stage timing, faster replies

Card t_09e48987, 2026-11-07, author sonnet-coder. Synthetic messages only. Nothing was restarted, no Mac, key, `~/.config/hass`, fleet model or real owner message was touched. Files: `reports/hass/fast-1/` (bench, raw results, prompt sizes).

## 1. Answers

1. **Ack method chosen: a text `👀`, not a tapback.** The tapback needs BlueBubbles' Private API (`/api/v1/message/react`; BlueBubbles docs: "requires the Private API"), which the runbook keeps off, and even with it on, BlueBubbles can only send the six classic tapbacks (love, like, dislike, laugh, emphasize, question): there is no 👀 tapback. I could not test the live server (it runs on the Mac, off limits); the new read-only `hass_forwarder.py ackcheck --config FILE` (one GET of `/api/v1/server/info`, sends nothing) lets the operator confirm `privateApi: false` on the real server.
2. **Three biggest speed wins (plain words):**
   - **Stop the model running on the slow CPU**: use the model the fleet already keeps on the GPUs. MEASURED by HASS-MODEL-1: 2-6 s per free-text request instead of 60-90 s. Needs card HASS-INTERP-OPENAI-1 plus the fleet operator's OK.
   - **Stop waiting for the one-minute catch-up**: "model-free commands answer in about a minute" matches the old 60 s catch-up poll exactly, which means the BlueBubbles webhook is probably not waking the forwarder (verify with the new stage log: `accepted via=poll`). This PR makes the poll 15 s and pulls replies every second for 3 minutes after an owner message. MEASURED: reply 2.4-3.3 s -> 1.5 s with a working webhook; 22-52 s -> 6-12 s without one. Fixing the webhook itself is worth the rest (operator card below).
   - **Keep the CPU model loaded and trim its prompt** (only until the GPU route is live): MEASURED 23-28 s per request kept loaded vs 60-90 s now; the prompt is 44,036 characters (about 12.6k tokens), 81% of it product descriptions; trimming is ESTIMATED to cut CPU prefill (34 s of 39 s compute) by about 3-4x.
3. **How fast the 👀 is (attempt versus confirmed, honestly).** Two different numbers, both seconds after the forwarder stored the message. **Attempt latency** = `ack-start` (the fresh \"paused?\" question to the host has been answered and the send begins). **Confirmed latency** = `ack-end` (the send call returned). In the bench (real forwarder, real host over real HTTP, BlueBubbles a stand-in) the attempt starts **0.07-0.23 s** after storing and, with a 0 s stand-in send, is confirmed 0.01-0.03 s later; with a stand-in send that itself takes 0.5 s / 1.5 s the confirmed time is 0.6 s / 1.7 s. **Nothing here proves \"within 2 s\" on the real Mac.** The real BlueBubbles AppleScript send time is **not measured** (ESTIMATE 1-3 s, and the Mac's own AppleScript queue may serialise sends that the forwarder starts side by side), and a send slower than 1.5 s is cut off and recorded `failed` although BlueBubbles may still deliver it. What the code does, and no more: each owner message gets its own ack worker, so its attempt starts straight away instead of waiting behind the sends before it (round 3 fix: four messages with 0.8 s sends used to *start* at 0.13 / 0.92 / 1.71 / 2.49 s and be *confirmed* at 0.93 / 1.72 / 2.51 / 3.29 s; now all four start together at 0.05-0.12 s and are confirmed at 0.86-0.93 s, three runs on this box, test-asserted with real 0.8 s sleeps); one attempt can still take up to 0.5 s (host question) + 1.5 s (send) = 2.0 s after its worker starts, so a confirmation can land after the 2 s budget. A 👀 that is *sent* but confirmed more than 2 s (`ACK_BUDGET`) after the message was stored is recorded **`late`**, not `sent`: it is not counted as on time and is visible as `outcome=late` in the stage log. One that has waited more than 10 s is `stale` and not sent. **Left explicitly for the operator**: read `ack-start`/`ack-end` (`outcome=sent|late|failed`) in the live stage log after deploy; that is the only real measurement of attempt and confirmed latency.

## 2. Part A: what was built (Mac forwarder + host)

- **When**: the forwarder stores a NEW message from the owner's own address in the owner's one-to-one chat (`msg.kind == new`, not `from_me`, `sender_key(sender) == sender_key(address in ownerChat)`, sent less than 120 s ago).
- **Own thread, so nothing slow can delay it and it can delay nothing** (round-2 fix 1 and 2). The ack runs on a dedicated dispatcher thread with its own SQLite connection to the spool, and (round-3 fix 1) the dispatcher only *claims* rows and starts **one worker thread per pending message** (up to `ACK_WORKERS` = 50 = the largest burst one catch-up query can accept; each worker has its own spool connection), so sends no longer queue behind each other. Measured on this box with real sleeps: 4 messages x 0.8 s sends all attempted at 0.05-0.12 s and confirmed at 0.86-0.93 s; 12 x 0.4 s all attempted within 0.41 s; 50 at once overlap their sends (a serial queue never overlaps two) but each worker commits to the spool, and on this disk the last attempts of a 50-burst started about 1.9-2.3 s after storing, so those are recorded `late` rather than dropped (the budget is not guaranteed for a burst of 50, only for the small bursts an owner actually sends). `Forwarder.cycle` accepts first (the webhook fetch, then the catch-up poll) and wakes the ack thread right after each, *before* the receiver post and the reply pull; the thread also looks every 0.25 s as a backstop. A slow reply send, picture, catch-up query or receiver post in the main loop therefore cannot hold the 👀, and a slow or failing 👀 send (or a 0.5 s host question that times out) cannot hold inbound delivery. What the two share: the spool file (every ack row is claimed with an atomic `UPDATE ... WHERE state='pending'` (pending -> checking, one transaction for the whole burst) and again checking -> sending before the send, so two threads or two processes can never send twice; a row left `checking` by a worker that died goes back to `pending` after 8 s, which is safe because nothing was sent in that state) and the nonce table. Unit tests that call `cycle()` without `start_ack()` run the same code inline.
- **Never**: a stranger in the owner chat, another chat or a group, Hass's own messages (including its own 👀), edits, reactions, a message found late by the catch-up poll (>120 s old), an ack that waited >10 s (recorded `stale`), while changes are paused, or when the host cannot be asked. The stranger is still forwarded exactly as before (the host decides; it records `ignored` and replies nothing).
- **Paused: fail closed, nothing cached** (round-2 fix 3). Every 👀 is preceded by a fresh sealed read-only `state` question to the host (0.5 s limit); the previous 30 s cache and 60 s local hold are gone. The host (`host.paused_flag`: round-3 fix 2 reads both databases in **one read-only connection** (`mode=ro`, the inbox attached) and one transaction, **the inbox first, then the flag**, then the flag again in a new transaction; any disagreement or error is paused. The order matters: the worker commits the pause flag first and only then marks the inbox message done, so a pause that has left the queue is always already in the flag, and one still being handled is still `pending` in the queue. The old order (flag, then queue, two connections) could miss a pause that moved between the two reads.) answers *paused* when (a) its pause flag is set, (b) a **pause command is still unread in its inbox queue** (the worker may be busy with a slow earlier message, so the flag is not set yet), or (c) it cannot tell (unreadable store, unreadable queued payload). The Mac adds its own durable, time-free check: no 👀 while a pause command, an unreadable message, or an earlier unresolved `new-message` doorbell is stored in the spool and not yet handed to the host (this also stops the pause command itself getting a 👀). No answer, an error, or an old host that does not know the op = no 👀, final for that message (never sent late). Remaining boundary, stated precisely: a 👀 can go out for a message that arrived *before* a pause command the forwarder had not yet seen; nothing can know of a command no component has seen, and the message did precede it.
- **Exactly once**: spool table `ack(provider_id PRIMARY KEY, state, ...)`; the row is created only when the inbound row is newly inserted (webhook, catch-up, replay and restart find it present), moves `pending -> checking -> sending` (committed before the send) `-> sent | late | failed`, and a `sending` row after a crash is never sent again (at-most-once beats a double 👀). No retry on failure. `late` = sent, but confirmed more than `ACK_BUDGET` (2 s) after the message was stored (also the outcome for an ack that only got to start after the budget: it still goes out, once, until `ACK_STALE` = 10 s; nothing required is dropped silently, and it is not counted as on time).
- **Never blocks**: every ack error is recorded and ignored; `ack()` itself is wrapped so even a broken table cannot stop the loop or the thread; the default ack sender clamps its HTTP timeout to 1.5 s and the host question to 0.5 s. These are limits on one attempt, not a guarantee of the 2 s budget (see answer 3).
- **Switch**: optional config key `"ack": false`. Deploy order: **host first, then Mac** (a new Mac against an old host sends no 👀 and breaks nothing; an old Mac against a new host is unaffected).
- **Commands that reply fast**: decision: **ack them too**. Measured command replies are 1.5 s at best (bench, 0 s BlueBubbles send) and 6-52 s when the webhook is silent; with the AppleScript send they are not reliably under 3 s, so the 👀 is not a double message in practice, and having the Mac guess which texts are commands would duplicate the host's parser and make the 👀 inconsistent. Revisit once the live stage log shows command replies under 3 s (one-line skip in `Spool.owner_arrived`).
- Tests (`hass/tests/test_fast_ack.py`, 65 tests, plus the unchanged forwarder/host/relay/receiver suites): owner acked once before delivery; stranger sender (no 👀, no reply, still recorded `ignored` by the real host); other chat, group, echo, no handle, reaction, edit, look-alike address, late message, stale ack; replay via webhook + catch-up + direct accept + restart = one 👀; crash mid-send never resends; paused/unknown (asked fresh for every ack); send failure and any exception swallowed; cycle order fetch -> ack -> post; end-to-end with the real forwarder, host Server, Receiver, Worker, Conversation (pause stops the 👀, resume restores it, replay adds none, the host's own echo never causes one). **Round 2** (reviewer's three cases, all with real waits and the real ack thread): a 1.2 s ack send ending in an error does not delay the receiver post (cycle < 0.8 s, post made while the send is still sleeping); a 1.5 s reply pull or a 0.8 s catch-up in the same cycle does not delay the 👀 (it goes out first, in under 0.5 s of acceptance); 12 messages x 2 threads on one spool = 12 👀; 25 messages through the cycle while the thread runs = 25 posts, 25 👀, no lock loss; the thread survives a raising sender and a broken table. **Round 3** (reviewer's two reproduced items): a burst of 4 messages with real 0.8 s sends starts every attempt within 0.5 s and confirms each within 2 s; 12 messages with 0.4 s sends; the 50-message page overlaps its sends and drops none; an ack past its budget is sent once and recorded `late` (also a send that is attempted at once but confirmed after the budget), one past 10 s is `stale`, more pending rows than workers are all still decided, a row left `checking` by a dead worker is retried once after 8 s. Pause race: with the real host, worker, store and forwarder, the worker moves a queued pause into the flag right after each statement of the host's read (before the first read, after the transaction opens, after the queue is read, after it closes); the answer is paused every time and the forwarder sends no 👀; a flag appearing between the two flag reads is paused; an unreadable inbox is paused. Pause: with the real host store and Conversation, a pause set on the host between two polls stops the next 👀 at once; a pause command queued at the host behind a slow message (flag not yet set) stops it; a failed or older-host state question stops it; `host.paused_flag` itself (unread pause variants, other queued text not blocking, unreadable payload = paused, read-only).

## 6. Limits

- BlueBubbles shapes remain UNVERIFIED on a real Mac; the bench uses a stand-in for BlueBubbles (0, 0.5 and 1.5 s sends) and a 0 s model. **The real send time of the 👀, and with it the real "within 2 s", is not measured; verify it from the live stage log (`ack-start`, `ack-end` with `outcome`) after the operator deploys.** No Mac, service or real message was touched.
- The host's HTTP server is single-threaded. The 0.5 s "paused?" question queues behind a request the host is already serving (for example a 2.5 MiB picture); then that message gets no 👀 (fail closed), never a late or unchecked one. How often that happens is unmeasured.
- Acceptance itself still runs in the main loop. A reply send or picture the main loop is already busy with (up to 10 s per send, five replies per pull) delays *accepting* the next webhook-announced message, and so its 👀; this delays the ack's *start* too, because the ack is queued at acceptance; the 2 s figure is measured from acceptance and is not a guarantee from the webhook. Card HASS-FWD-THREADS-1 (move the reply pull to its own thread) removes it; not built here (a second SQLite-owning thread in the delivery path needs its own review).
- The bench shares one clock for both machines; the live join of Mac and host logs depends on their clocks being in step. The stage log's `reply-queued` joins a reply to the message being handled, exact because replies are flushed per message.
