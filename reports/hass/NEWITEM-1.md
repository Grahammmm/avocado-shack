# HASS-NEWITEM-1: new-item skill (house-style picture, description, maker) from one photo and one plain message

Repo Grahammmm/avocado-shack, branch `rb/hass-newitem-1`. Synthetic photos and messages only. Nothing was published, no live site, service, model, approval, owner or publish logic was touched. Built and tested locally; review round 1 (Sol, 4 must-fix items) is answered in section 7; **not yet merged**.

## 0. Answer in one paragraph

Hass already takes a photo, stores the original, strips its metadata, asks "which product and what does the photo show", lets the LLM interpreter propose `product.add` / `maker.add`, runs the claims gate, previews and waits for `yes <code>`. It does **not** make a new item look like the others: today the "web copy" is the owner's original with metadata removed (any size, any background), the description is whatever the interpreter writes, and a new maker is whatever it is told. This PR adds the missing half: a **measured style spec** (`hass/style/house-style.json`), a **style check** for pictures, descriptions, makers and product records, a deterministic **picture renderer** (800x800, warm ivory, centred, soft shadow, no metadata), and a **drafter** that turns one message plus one photo into the typed ops the existing path already accepts. The approval path is untouched. One short seam (section 5, card 1) plugs the renderer into the existing install step.

## 2. Part A: the house style, measured from the repo

Source: 170 active products, 26 makers, 170 pictures (`hass/style/house-style.json`, rebuilt by `python3 hass/house_style.py measure --out hass/style/house-style.json`; `verify` says if it drifted). Every number below is in the JSON with min/p05/p25/p50/p75/p95/max.

**Pictures.** All 170: **800x800, 1:1, RGB WEBP** (quality about 84, produced by `optimize-images.cjs`), no EXIF. Median 62 KB (p05 31 KB, p95 99 KB). Named `photo-product-NNN.webp`. Background **warm ivory, median rgb(254, 248, 236)** (R 249..254, G 237..251, B 223..243), nearly flat (edge variation median 2.4 levels). Subject: largest side **90% of the frame (p05 79%, p95 97%)**, height 79%, centred (x +0.012, y +0.006), area 40% of the frame, 8% bottom margin (p05 4%). Soft contact shadow under the foot (about 3 levels darker than the ivory on average, p95 8.6). Subject brightness 141 of 255 (p05 89, p95 185), colour strength 0.48 (0.26..0.70): true packaging colours, no props, hands, text overlays, prices or borders; soft diffuse light from the upper left. Catalog pictures are **AI illustrations made from shelf photos** ("background-extraction" prompts in `image-generation-log.json`), so a deterministic render can match framing, background, shadow, size and format but not the studio relighting. On the page: square box, `object-fit: contain`, page colour `#f5f0e6`.
**Catalog illustration vs owner photo.** `shop.js installedImage()` treats only `assets/products/photo-<16 hex>.(jpg|png)` as an owner photo: alt = `imageAlt` as written; anything else gets ` (illustration)` appended and the shop-wide note "Some product pictures are illustrations". 0 of 170 live products are owner photos today. A new item must therefore be saved as `photo-<sha16>.jpg` (the render is JPEG, not WEBP, so the existing name rules, `HOME_IMAGE_RE` and the "photos to take" list keep working; WEBP parity would need a pattern change, card 6).
**Alt text.** No live product has `imageAlt` (the page uses the name + " (illustration)"). House alt for an owner photo: the product's name, plus "in a <container>" only if Michael said it; never a file name, never "photo of".

**Descriptions (170).** 2 sentences (143) or 3 (27); **59..167 characters, median 133**; 20..31 words; 5..15.5 words per sentence. Structure: sentence 1 says what it is (for a named maker: `<Thing> from <Maker> in <Town>.`, e.g. "Apple juice from Fair Hills Farm in San Miguel."), the following sentence(s) are an imperative serving suggestion ("Spoon a little beside cheese or onto buttered toast"); items with no maker are two serving sentences. Openers after the first sentence: keep 13, break 11, slice 9, coffee 8, butter 7, eat 6, put 6, then 5, give 5, finish 5. Always ends with a full stop; curly apostrophes (31 use them, 0 straight); **never** a digit (0 of 170), `!` or `?`, emoji, `$ < > {{ }}`, price, size, quantity or hype word (absent: amazing, delicious, perfect, premium, gourmet, authentic, healthy, natural ...); claim words appear in 11 of 170 and each is on a documented source (organic 8, estate 1, made in 1, unfiltered 1). Repeated sentences are normal (all Cal Poly chocolates share one closing line).
**Makers (26 shown).** Fields `name`, `place`, `story` (+ `url`, `hidden`); key = name (26 of 26); place `Town, State` (or "California’s Central Coast", "Northern California"); story 3 sentences (20 of 26), **239..297 characters**, written from the maker's own page, which `url` (https, all 26) links; the card shows "Based in <place>" and a "Meet the maker" disclosure with the story and "See all N from <maker>".
**Records.** Product fields `id name brand category image description producerKey displayBrand status` (+ `imageAlt addedOn available available_on`); id `photo-product-NNN`, next = highest + 1 (175 today); unknown producer = brand "Producer not identified", displayBrand "From the market", producerKey null (62 items); 9 shelves: Fruit 13, Vegetables 52, Dairy & cheese 20, Eggs 1, Meat 3, Pantry 61, Drinks & coffee 15, Bread 4, Flowers 1. Names: sentence case, no digits or sizes (32 of 170 begin with the maker). **No prices and no sizes on the site**: `$` is rejected in content text and the interpreter prompt says so.
**About page.** There is no separate about page: the "about" content is (a) the per-maker disclosure above and (b) the single "COME ON IN" store story (`store.story`, 400 characters, edited by `store.set_story`). A new item adds only (a).

At least 10 real examples of each are in the JSON (`pictures.catalog.examples` 12, `descriptions.examples` 14, `makers.examples` 13).

**Style check** (`hass/house_style.py`): `check_image(bytes)`, `check_description(text, owner_text=)`, `check_maker(rec)`, `check_product(rec, makers)` return `{score 0-100, pass, hard_failures, checks[]}`. Hard checks fail the item whatever the score. Calibration: all 170 live descriptions, 26 makers, 170 product records and 170 pictures pass their own checks; a raw phone photo fails (size, metadata, background); a price, digit, unstated or negated claim, one-line or over-long description fails; **a picture that still has its photo background fails even when the renderer letterboxed it onto ivory** (outer frame check plus a new hard check, "no photo background left inside the product": the number and area of background-coloured patches that do not reach the edge, 0-17 patches in the catalog vs 45 for the checkered red cloth).

## 3. Part B: the prototype

`hass/newitem.py` `draft(message, photo, content=...)`; `hass/newitem_render.py` `render(photo)`; `hass/newitem_synthetic.py` makes the test photos; `hass/newitem_demo.py` regenerates everything under `reports/hass/newitem-1/`.

* **Picture** (Pillow, deterministic, no model): turn the pixels upright from the EXIF tag; fit the border colours as a plane and take what differs as the subject (cast shadow and stray blobs dropped); straighten a leaning product (3..20 degrees); scale so the largest side is 90% of 800; centre on rgb(254, 248, 236) with the measured soft shadow; nudge exposure into the measured brightness band only; save JPEG q90 down to q74 to stay under 1.3 times the catalog p95 size, **with no metadata at all** (the test proves EXIF device, time and GPS are gone). Same bytes in, same bytes out (test). Result on the 8 synthetic cases: 6 plain-background cases (white sheet, grey wall, bench, tilted, phone photo with rotation tag and GPS, PNG, transparent cut-out) become house pictures scoring 90-100; a 480x360 photo is flagged "enlarged 3.2 times, will look soft"; **two busy backgrounds (dark wood stripes, red cloth) are not faked**: the whole photo is letterboxed, `isolation` = "fallback", the draft says it will not match, and `status` becomes `draft-with-warnings`. Cutting a product out of clutter needs a vision/image-edit model (that is how the catalog was made); `label_reader.py` reads label text only and does not isolate anything, so it is not used for this. Known roughness: the base outline of a cut-out is slightly stepped when the photo has its own cast shadow.
* **Facts** come from Michael's words only. The LLM reads the message (`EXTRACT_PROMPT`, JSON keys `name maker place story kind shelf container size price availability use url`, values copied from the message); `extract_facts` is a regex floor for offline use (it reads the item from his first sentence, so "They grow the peppers" later on cannot rename a hot sauce). `ground()` drops any value not traceable to the message, any value he only said with a negator ("not organic", "do not keep bees"), and any claim word he did not affirm (the claims gate's own negator rule). A story sentence must come from ONE sentence he wrote, its words in his order, with the same polarity. **Shelf and availability are never taken on trust from a reader**: the shelf must be one he named ("on the dairy shelf"), otherwise the same-kind majority shelf from the catalog is used; the availability must be what his phrases show ("got in" -> yes, "sold out" -> no, "only a few" -> limited), otherwise none is set. Dropped or corrected facts are listed in `dropped` and are never used.
* **Description**: template in the measured voice: `<Thing> from <Maker> in <Town>.` (town only from the maker record or his words) plus a serving sentence taken **verbatim from the existing same-kind items** (honey borrows from the two live honeys) or built from his words ("Great on toast" -> "Try it on toast."), or two catalog sentences when the maker is unknown; claim-free by construction (`_serving_ok` drops any sentence with an unaffirmed claim term, proper noun or digit). A model-written description (`writer=`) is accepted only if (1) its first sentence uses only the facts' own words plus plain glue (`from in by a an the of and at near`), (2) later sentences are serving suggestions in the catalog's own words and openers, (3) no ingredient/origin/history word (`blended made since family century old ... from by near`) appears unless the facts carry it, (4) no negation, number or unaffirmed claim word, and (5) it passes `check_description` and the proper-noun test; otherwise the template is used and the reason is recorded in `writer_rejected`. This is deliberately conservative: it rejects some harmless rewrites (they fall back to the template) rather than let an invented fact through.
* **Maker**: reuse the record when his message names a maker already on file; else `maker.add` with name, **place exactly as he wrote it (must be "Town, State", else ONE question)**, a story built only from his sentences ("They keep bees on the hill" -> "<Maker> keeps bees on the hill."), else the one-line note "<Maker> is based in <place>." (the model requires a story; there is no way to say "no story" yet, card 4).
* **Shelf** from his words or the majority shelf of the same kind in the catalog (honey -> Pantry); otherwise the question "Which shelf ...". **Availability** `product.set_availability` is added only when today's shelf check is current (the op is refused otherwise and would refuse the whole draft); else it is listed as left off.
* **Price, size, claims**: never written to any field. `left_off` lists them with the reason ("the site shows no prices"), so Michael is told, not silently stripped. A claim he voices (organic, local) is left off with its reason.
* **One question**: `question()` returns at most one, in priority: what is it, where is the new maker (town and state), which shelf. The label reader's "The label looks like ..." line is used when the message names nothing.

Example (`reports/hass/newitem-1/drafts.json`): *"got in some Cal Poly honey, jar of 8oz, $9"* -> `product.add{name "Cal Poly honey", brand "Cal Poly", category pantry, producerKey "Cal Poly", imageAlt "Cal Poly honey in a jar", description "Honey from Cal Poly in San Luis Obispo. Spoon a little beside cheese or onto buttered toast; give it a chance to be tasted on its own."}` (+ `set_availability yes` when the check is current); left off: price ($9), size (8oz). Descriptions, picture and records all pass the house check.

**Before/after, in a real browser** (`hass/newitem_preview.py`, run: `PLAYWRIGHT_MODULE=<playwright> python3 hass/newitem_preview.py`; output in `reports/hass/newitem-1/preview/`). For each of three synthetic cases the shop's own pipeline builds the page twice and headless Chromium shows the new card next to two existing cards that the same search lists (the site now puts new products first, so they follow it), with the maker note open, on a phone (390 px) and a desktop (1280 px) page:

* BEFORE = what the shop shows today: the photo with its metadata removed by the existing `media._jpeg_copy`, Michael's words as the description, no maker entry.
* AFTER = the draft.

How it reuses the existing machinery: the draft's typed ops are applied to an in-memory catalog by the REAL op handlers (`ops.catalog._maker_add / _product_add / _product_set_availability`; `photos.install` is replaced by the picture's path because an offline run has no media store), `sitegen.render` makes the site files, `preview.Previewer` copies the tracked site, lays the files and the picture over it, serves it on 127.0.0.1 with an empty throwaway database and runs `hass/newitem_screenshot.cjs` (GET/HEAD to that origin only). The script types the search into the page's own box, brings the new card into view and records, as booleans, whether the new card matches its neighbours: **same picture box and fit, same description type, same title type, same card width**, and shows the drafted picture, alt text, description, maker name, maker story and availability word. All checks are `true` for all six runs on both viewports (`preview.json`: 14 per viewport for AFTER, 12 for BEFORE). Files (each pair: BEFORE | AFTER):

What the captures show (read by eye, not only by check): the AFTER card sits in the same layout as the existing cards (same square picture box on the ivory, same type, "Based in <place>", description, expanded "Meet the maker" note, "New" badge and "Available today" word, which the site gives any new item); BEFORE shows the white sheet or grey wall of the photo inside the card, the raw message (with "$9" and "8oz") as the description, "From the market" in place of the maker and no maker note. **What does not match, honestly:** (1) the synthetic photos are flat vector drawings of a jar, bottle and bag; the catalog is photographic, so the product itself looks plainer than its neighbours even though its background, framing, size, shadow and layout match (that is a property of the made-up photos, not of the renderer; a real photo will show whether relighting matters); (2) the 480x360 coffee photo is enlarged 3.2 times, so the product fills less of the frame and is soft, and the draft says so (`draft-with-warnings`); (3) a maker with no story gets the one-line "<Maker> is based in <place>." note, which is thin beside the real stories (card 4); (4) the "New" badge and availability word make the new card's header taller than its neighbours' on the same row, which is the site's normal behaviour for any new item. ## 4. Part C: flow, with no change to approval or safety logic

1. Photo arrives: unchanged (`_photo`: check, store original, needs-details draft, label reader may add its question).
2. Message arrives (caption or answer): the interpreter step is where the LLM digests the natural language. The skill supplies `EXTRACT_PROMPT` and, for the description, `writer_prompt` (voice rules + real same-kind examples + only the facts). Its output is validated (`ground`, `check_*`) before it becomes a draft.
3. Ops: `maker.add` (if new), `product.add{photo, imageAlt, ...}`, `product.set_availability` (if the check is current): the same typed ops, so `editor.prepare`, `claims.unstated`, preview and "yes <code>" run as before. A failed hard check or a fallback render is shown to Michael in the reply, and the draft is not marked clean.
4. Install: `photos.install` calls `_web_bytes(root, sha)`; the seam is to return `render(web_copy bytes)` as `(jpeg, "jpg")` (the test patches exactly this). Same input gives the same bytes, so `install`'s "same name, different bytes" refusal cannot fire on a re-render.
5. Preview: the existing `Previewer` shows the card with the new picture; writer commit stores `photo-<sha16>.jpg`; undo hides the product and keeps the file (existing behaviour). Publish is untouched (`sitegen --publish`, G's decision).

## 7. Review round 1 (Sol, PR head 38c5fe53) and what changed

1. **Fact-only text and polarity.** Writer descriptions: first sentence fact-only, later sentences catalog-voice serving suggestions, no ingredient/origin/history words, no negation, claim words only when affirmed (section 3). Story sentences are matched to one source sentence of his, in order, same polarity.
2. **Shelf and availability are grounded**, not allow-listed: model `shelf: meat, availability: no` for `got in some Cal Poly honey` now gives Pantry and `yes` (both recorded in `dropped`); with no availability phrase none is set.

The spec JSON was re-measured (`holes`, `hole_area` added) and `verify` matches.
4. **Browser before/after beside existing items**: section 3 and `reports/hass/newitem-1/preview/`.
